# 보유 도메인 관리

사용자가 가진 목록에서 브랜드·서비스별 주 도메인, 보조 도메인, 이전 예정, 정리 후보를 나눈다.
이름만 보고 소유권을 추정하지 않는다. 확인된 목록과 읽기 권한이 있는 설정을 이용한다.

| 도메인 | 사용 목적 | 등록기관 | 만료일 | 갱신 비용 | 자동갱신 상태 | 다음 행동 |
|---|---|---|---|---|---|---|

모르는 값은 미확인으로 둔다. 인증 코드, 비밀번호, 전체 결제 정보는 목록에 넣지 않는다.

## 갱신과 정리

실사용 여부, 이메일·로그인·인쇄물·광고에서의 의존성, 사칭 가능성, 유지 비용을 함께 본다.
접속이 없는 도메인이라도 메일이나 계정 복구 주소로 쓰일 수 있으므로 곧바로 해지 후보로 확정하지 않는다.
자동갱신 여부와 결제수단 유효성, 알림을 받을 독립적인 연락처를 사용자가 확인하도록 정리한다.
날짜는 등록기관 기준과 시간대를 확인하고, 알림 등록은 요청받은 일정 도구가 있을 때만 실행한다.

## 이전과 연결

이전 제한·잠금·인증 코드·등록자 확인·남은 기간과 수수료는 해당 기관의 최신 정책을 읽는다.
gTLD의 최초 등록·기관 간 이전 직후 제한과 등록자 변경 후 잠금을 구분한다. 등록자 변경 잠금의 사전 해제 선택권 제공 여부도 기관마다 확인한다.
이전하려는 도메인의 연락처를 먼저 바꿨다가 이전이 묶이지 않도록 작업 순서를 검토한다. 잠금 해제와 AuthInfo를 보고서에 공개하지 않는다.
변경 전 DNS 레코드와 서비스 의존성을 읽고, 웹·메일 유지 순서와 되돌릴 방법을 마련한다.
루트·www, 리디렉션, HTTPS, MX, SPF, DKIM, DMARC는 실제 사용하는 서비스 범위에서 검토한다.
DNSSEC의 DS 레코드와 네임서버 변경이 서로 맞는지도 확인한다.
기관 이전과 사이트 주소 변경은 별개의 작업이다. 주소까지 바꾸면 기존 URL별 목적지를 대응시키고 관련 없는 주소를 모두 첫 화면으로 보내지 않는다.
검색 이전은 영구 리디렉션·canonical·사이트맵·허용된 Search Console 주소 변경을 함께 준비한다. 리디렉션은 일반적으로 적어도 1년 유지하는 계획을 세운다.
옛 도메인의 메일·계정 복구·인쇄물 의존성이 남으면 검색 이전이 끝났어도 갱신 중단을 권하지 않는다.
지금 요청이 검토라면 변경안을 전달한다. 실제 변경 요청이 있어야 설정에 적용하며, 적용 후 웹과 이메일을 각각 확인한다.
이전·갱신에 결제가 필요하면 사용자가 처리한다.
