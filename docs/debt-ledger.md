# 부채 대장 — 알면서 남겨 둔 것

알고도 지금 안 고친 것만 적는다. 여기 없는 임시조치는 땜빵으로 친다.
고친 것은 줄을 지우지 말고 "갚음" 줄을 붙인다.

---

## 1. 3단이 받은 최신 화면 한 장을 4단이 또 받는다

- **무엇**: 3단(가장 최근 모습 보기)이 내려받은 앞페이지 한 장을, 4단(옛 화면 전수 정독)이
  다시 한 번 내려받는다. 도메인당 본문 요청 1회가 그냥 버려진다.
- **왜 지금 안 고쳤나**: 4단은 "대표 화면 고르기"를 자기 규칙으로 새로 하므로, 3단이 받은 장을
  물려주려면 두 단이 같은 장부를 공유해야 한다. 순서 재배치를 막 끝낸 참이라 같은 자리를 또
  건드리면 판정이 흔들린다.
- **되돌릴 조건**: 4단 대표 화면 선정이 한 달간 안 바뀌면, 받아 둔 본문을 넘겨주는 장부 하나를 둔다.
- **기한**: 2026-09-30
- **근거**: `tests/test_pipeline.py` 본문 요청 수 = 연도 수 + 3
- **갚음: 2026-08-23** — 대표 화면 고르는 규칙은 손대지 않고, 웨이백 클라이언트 안에
  **받아 둔 본문 장부**를 하나 두어 해결했다. 한 번 받은 저장분은 내용 지문(digest)으로
  기억해 두고, 같은 장을 다시 달라고 하면 웨이백을 두드리지 않고 장부에서 꺼내 준다.
  두 단이 장부를 공유할 필요도, 판정이 흔들릴 일도 없다 — 읽는 내용은 그대로이고
  두드리는 횟수만 준다. 장부는 도메인 하나가 끝나면 함께 사라진다.
  실패(못 받음)는 장부에 적지 않는다 — 웨이백은 바쁜 날 같은 주소를 몇 초 뒤에 열어 준다.
  실측: `tests/test_pipeline.py` 본문 요청 수 연도 수 + 3 → **연도 수 + 2** (도메인당 1회 절약).

## 2. 3단에서 찾은 위험 흔적이 스팸 확정이 아니면 버려진다

- **무엇**: `pipeline.py`의 `screen_recent` 가 최신 화면에서 계산한 규칙 검사 결과는, 그 자리에서
  탈락이 확정될 때만 결과에 남고 아니면 통째로 사라진다. 그 화면이 하위 주소였고 4단 대표에
  안 뽑히면 그 증거는 다시 볼 수 없다.
- **왜 지금 안 고쳤나**: 3단 결과와 4단 결과를 합치는 규칙(어느 쪽 판정을 이기게 할지)이 정해져
  있지 않다. 아무렇게나 합치면 같은 흔적이 두 번 세어져 감점이 겹친다.
- **되돌릴 조건**: 합치는 규칙을 정하면 3단 findings 를 4단 입력에 얹는다.
- **기한**: 2026-09-30
- **2026-08-23 갱신 — 아직 못 갚음.** 1번을 갚으면서 3단이 받은 **본문**을 4단에 물려주는
  길은 생겼다(받아 둔 본문 장부). 하지만 3단이 본 화면을 4단의 읽은 목록에 끼워 넣으면
  규칙 검사가 보는 화면 수가 달라지고, 그러면 파킹 비율 같은 값이 움직여 **판정 결과가
  바뀔 수 있다.** 이번 대청소는 "빼기"라 판정을 바꾸지 않는 것이 조건이었으므로 손대지 않았다.
  남은 일은 코드가 아니라 결정이다 — 3단 판정과 4단 판정 중 어느 쪽을 이기게 할지 정하는 것.
  그것까지 정해야 이 줄을 닫을 수 있다.

## 3. 본문이 많아 쪼개 읽을 때 구간별 "추천 주제"가 버려진다

- **무엇**: `analyze/ai.py` 의 부분 응답 병합 목록(`_PARTIAL_KEYS`)에 `recommended_topics` 가 없다.
  묶음별로 나온 추천 주제는 버려지고 마지막 통합 호출이 새로 짓는다.
- **왜 지금 안 고쳤나**: 그냥 합치면 비슷한 추천이 열 개씩 쌓인다. 중복을 걸러 3~5개로 줄이는
  규칙이 필요하다.
- **되돌릴 조건**: 추천 주제 중복 제거 규칙을 정하면 병합 목록에 넣는다.
- **기한**: 2026-09-30
- **갚음: 2026-08-23** — 중복을 거르는 "규칙"을 따로 만들지 않았다. 낱말이 겹치는지 세는
  기계식 거르개는 뜻 판단을 기계에게 맡기는 짓이라 애초에 두면 안 되는 물건이다.
  구간별 추천을 그대로 통합 호출에 실어 보내고, 겹치는 것을 하나로 합쳐 3~5개만 남기는
  일은 **통합 호출이 뜻을 보고** 하게 했다(그 호출은 원래 전체를 합치라고 부르는 자리다).
  묶음 하나가 실어 보내는 추천은 앞의 3개로 끊어 통합 호출의 입력이 불어나지 않게 했다.
  추천 주제는 화면에 보여 주는 항목일 뿐 판정에는 쓰이지 않아 판정은 그대로다.
  시험: `tests/test_ai.py::test_topics_found_in_each_chunk_reach_the_final_merge`

## 4. 보고서 만들기가 화면에 연결되어 있지 않다

- **무엇**: 서버에 보고서 만들기(`POST /api/report`)와 완료·실패 알림이 다 있는데, 화면에 그것을
  누를 단추도 실패를 받아 보여 줄 자리도 없다. 주소를 직접 쳐야만 볼 수 있다.
- **왜 지금 안 고쳤나**: 단추를 어느 화면 어디에 둘지는 화면 설계 결정이라 코드 정리 범위 밖이다.
- **되돌릴 조건**: 운영자가 보고서 단추 자리를 정하면 배선한다.
- **기한**: 미정(운영자 결정 대기)
- **근거**: 2026-08-22 현행화에서 발견, `DESIGN.md` §8에 기록됨
- **2026-08-23 갱신 — 아직 못 갚음(그대로).** 다시 확인해 보니 상태는 그대로다.
  화면 쪽 코드에 `report_ready`·`report_error` 를 듣는 자리가 한 곳도 없고, 보고서로 가는
  단추도 없다. 특히 **보고서 만들기가 실패해도 화면은 아무 말을 안 한다.**
  단추를 어디에 둘지는 화면 설계라 이번 대청소(빼기)의 범위 밖이다 — 운영자가 자리를
  정해 주면 그때 배선한다.
